# 原 Base＋Small 模型实时性实测

日期：2026-10-31。测量状态：已完成。

## 结论

在本机 RTX 4060 Laptop GPU、原 FP32 推理路径和当前输入尺度下，原 Base 平均约 4.40 秒/张，原 Small 约 4.57 秒/张，Base＋Small 四视图约 18.86 秒/张。**当前实现不满足常见的视频实时处理要求，也不适合作为连续运动接近时的高频视觉反馈。** 停车后的低频观测是否可接受，要结合采摘节拍与定位误差单独评估。

这是当前代码与运行环境的热运行速度，不是模型架构的理论速度上限，也不是 RTX 3080 的结果。两份原权重保持原样，本次没有训练或降低输入尺度、候选数量。

## 1. 测量条件

| 项目 | 设置 |
|---|---|
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU，物理显存 8188 MiB |
| CPU | Intel Core i7-13650HX；PyTorch CPU 线程数 4 |
| PyTorch | 2.12.1+cu132 |
| 数值配置 | FP32；matmul TF32=False；cuDNN TF32=True |
| 图像 | 同一随机清单的 8 张 PApple VAL 图，原图 1300×1300 |
| 模型输入 | 原预处理，短边 1024、最大边 1280；本批实际 1024×1024 |
| batch | 1，串行逐帧处理 |
| 单模型预热 | 各 10 次；随后另跑 8 张分阶段诊断，再运行 2 轮正式计时，共 16 帧 |
| 四视图预热 | 双权重 GPU 常驻后先跑 2 次组合预热，再跑 8 张分阶段诊断，随后 8 张正式计时 |
| 显示阈值 | confidence≥0.75；原生 V/A 掩膜阈值 0.5 |
| 四视图候选 | 保留全部原始候选，使用原 `flip_tta.py` 参数融合 |

计时从**已解码、位于 CPU 内存中的 RGB**开始。包括原预处理、输入传输、模型计算及所列输出处理。排除磁盘读图、权重加载及哈希、GT 审计、图片保存、显示、相机采集、机器人通信与控制。因此这些数值不能直接称为整机采摘闭环延迟。

## 2. 整帧正式计时

主测量使用 `perf_counter` 墙钟，在整帧首尾执行 CUDA 同步；分阶段诊断单独运行，不与主统计混算。FPS 按 `总帧数/总耗时` 计算，等于平均单帧耗时的倒数。

| 配置 | 输出终点 | 正式计时帧数 | 平均秒/张 | 中位秒/张 | 样本 P95 秒/张 | FPS |
|---|---|---:|---:|---:|---:|---:|
| 原 ConvNeXt-Base | 原图单视图；V/A 原图二值掩膜就绪 | 16 | 4.400 | 4.400 | 4.547 | 0.227 |
| 原 ConvNeXt-Small | 原图单视图；V/A 原图二值掩膜就绪 | 16 | 4.569 | 4.514 | 4.820 | 0.219 |
| 原 Base＋Small 四视图 | 四视图串行；框和分数融合完成 | 8 | 18.857 | 18.225 | 21.329 | 0.053 |

P95 仅是这批有限样本的经验分位数；单模型 16 次观测来自同一 8 张图的两轮重复。它不是长时间运行的稳定性或最坏时延保证。

四视图本身没有掩膜融合逻辑，其计时终点是生成全部融合框和分数；最终 `0.75` 筛选计数在计时终点后执行。不能将该行称为四视图融合轮廓就绪时间。

## 3. 统一查看框及分数就绪时间

| 配置 | 平均秒/张 | FPS |
|---|---:|---:|
| 原 ConvNeXt-Base | 4.395 | 0.228 |
| 原 ConvNeXt-Small | 4.565 | 0.219 |
| 原 Base＋Small 四视图 | 18.857 | 0.053 |

当前原始运行路径的输出解码会同时校验并拷回紧凑 ROI 掩膜，单模型框就绪时间也包含这部分工作；这不是另行裁剪分支后的最小框检测耗时。单模型之后的 V/A 贴回只增加几毫秒。

## 4. 独立分阶段诊断

下表来自额外的 8 张诊断帧，在阶段边界执行 CUDA 同步。用于判断开销分布，不直接相加替代第 2 节的正式整帧统计。

| 配置 | 预处理 ms | 输入传输/翻转 ms | 模型调用 ms | 输出解码 ms | 单模型掩膜贴回 / 四视图融合 ms |
|---|---:|---:|---:|---:|---:|
| 原 ConvNeXt-Base | 12.05 | 1.58 | 4356.13 | 16.02 | 4.10 |
| 原 ConvNeXt-Small | 15.30 | 1.69 | 4528.93 | 15.85 | 4.91 |
| 原 Base＋Small 四视图 | 15.40 | 1.75 | 17741.42 | 64.18 | 104.74 |

主要耗时集中在模型调用阶段。它包括骨干/FPN、候选生成、ROI 处理、掩膜分支和模型内部去重等，不是纯骨干 CUDA kernel 的耗时。最后把掩膜贴回原图所花的几毫秒，不包含模型内部双掩膜 NMS 的计算。

代码核查表明，模型会在最终筛选前处理大量候选区域，最终只显示少量苹果并不意味着只计算了同样数量的 ROI；内部双掩膜去重也涉及循环、采样及同步。这些是后续应单独剖析的阶段，目前没有逐算子数据证明哪一项占主导。Small 在这批数据中没有表现出明显的速度优势，不能仅凭骨干更小便认为整条推理路径会更快。

以上为当前 Python 进程由 PyTorch 统计的显存，不包含桌面或其他程序。四视图测量时两份权重同时驻留 GPU；没有将权重在 CPU/GPU 间逐帧换入换出。单模型测量时另一模型位于 CPU。

## 6. 结果一致性与后续工作

正式与诊断帧的框和分数均与上一轮原模型预测按原顺序核对，最大允许差为 1e-4，全部通过；原始差值保存在每帧记录中。两份权重 SHA256、严格恢复结果及源码前后哈希也已保存。

后续应优先保留原权重，对模型内部做 CPU/CUDA 联合性能分析，再定位冗余计算、调度与同步开销。任何影响数值或候选筛选的加速改动，都需要回到完整 VAL 复验 Precision、Recall 和掩膜质量。当前没有证据承诺某项优化能达到 10、20 或 30 FPS。

本次测量没有检验深度定位、时序跟踪、运动补偿和机械臂闭环。
