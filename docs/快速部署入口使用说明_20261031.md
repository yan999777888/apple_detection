# 原强模型快速部署入口使用说明

本入口使用原 ConvNeXt-Base、ConvNeXt-Small 权重，不训练、不替换模型、不读取 GT。它供单张 RGB 图片试用和部署联调；输出统一标记为 `candidate_pending_full_VAL`。原 Base 单图的 FP16、ROI chunk64、前 NMS 0.35 路径已完成一次真实 GPU 冒烟测试，成功导出 6 个实例及 V/A PNG/NPZ；其他组合及完整 VAL 精度仍待对应验收，不能把一次图片输出当作完整 VAL 结论。[冒烟记录](F:/研究生毕业设计/模块一定位补偿以及预测/apple_detection/reports/fast_deploy_20261031/predict_cli_gpu_smoke/metadata.json)。

原四视图强基线的已验证结果是 P＝94.4343%、R＝90.0261%。该结果属于原始 FP32 评估流程。新入口的 FP16/BF16、更大 ROI chunk、batch2 或局部裁剪属于独立部署设置，需用对应完整 VAL 和目标场景验收；不继承原基线的精度保证。两份原权重保持原样，每次加载均核对固定 SHA，并严格恢复所有参数。

## 1. 启动 F 盘环境

在 PowerShell 执行：

```powershell
Set-Location -LiteralPath 'F:\研究生毕业设计\模块一定位补偿以及预测\apple_detection'
. .\scripts\runtime_f_drive.ps1
& $ApplePython -B .\scripts\predict_fast_image.py --help
```

`runtime_f_drive.ps1` 使用已有 F 盘 Python 环境，并把模型缓存、临时文件等定向到 F 盘。需要可用 CUDA；不支持时入口会报错，不会偷偷换成其他模型。`--output` 必须是新的 F 盘目录，已有结果不覆盖。

## 2. 单模型原图识别及轮廓

将示例的图片路径换成自己的 RGB 文件：

```powershell
& $ApplePython -B .\scripts\predict_fast_image.py `
  --image 'F:\待识别图片\apple.jpg' `
  --output 'F:\苹果部署试验\base_001' `
  --model base --precision fp16 --roi-chunk-size 64 `
  --pre-nms-threshold none
```

`--model small` 使用原 Small。默认最终置信度为 0.75，短边为 1024、长边上限为 1280；模型内部按原方式补齐到 32 的倍数。默认 `--roi-precision autocast` 让 ROI 卷积参与选定的混合精度；`--roi-precision fp32` 提供较保守的 ROI 回退。ROIAlign、解码、最终概率及原 exact tiled dual-mask NMS 使用 FP32。没有用未校准的初始分类 logits 提前删除候选，也没有替换成近似掩膜 NMS。

主要输出：

- `input_rgb.png`：保存到新目录的 RGB 副本，原输入不改。
- `input_view.png`：实际送入预处理的原图或用户指定裁剪。
- `predictions.json`、`metadata.json`：检测、坐标、权重 SHA、配置、精度和运行记录。
- `prediction_boxes.png`：全图坐标的框预览。
- `visible_contours.png`、`amodal_contours.png`：真实二值掩膜轮廓预览，青色为可见 V，粉色为完整 A。
- `<model>_native_roi_masks.npz`：最终过阈值实例的无损 float32 ROI V/A 概率、分数、原预测索引和对应框。它不是整个全图的浮点掩膜堆栈。
- `masks/<model>/`：按冻结 `paste_roi_mask(..., mask_threshold=.5)` 贴回原图尺度的二值 crop PNG。JSON 同时记录 crop 内窗口与全图窗口，不能把小 PNG 直接当作全图尺寸图像。

完整轮廓中被遮挡的部分是模型预测，不是真实深度或果梗方向。这里的 V/A 只属于该模型的原图单视图。

## 3. 原 Base＋Small 四视图

```powershell
& $ApplePython -B .\scripts\predict_fast_image.py `
  --image 'F:\待识别图片\apple.jpg' `
  --output 'F:\苹果部署试验\fourview_001' `
  --model four-view --precision fp16 --roi-chunk-size 64 `
  --pre-nms-threshold none
```

每个模型分别对原图与水平翻转图做 batch2，翻转框还原后按强基线固定规则融合。Base、Small 依次各加载一次，一次仅驻留一个 GPU 模型。**这个模式只输出框和分数，不输出或声称融合像素级掩膜。** 四个 `*_boxes.json` 保留融合输入，便于检查。

FP16/BF16 和 batch2 会改变数值运算过程；不能保证框、分数、NMS 结果或掩膜逐像素等同原 FP32 串行基线。`--precision fp32 --roi-precision fp32 --roi-chunk-size 8` 可用于较保守的对照，但四视图仍是本入口的 batch2 路径，不能自动称为已经通过原基线复现。

## 4. 前 NMS 阈值与精度边界

`--pre-nms-threshold` 支持 `none`、`.35`、`.70`、`.75`，默认 **none**。它作用于原最终分类分数，原候选排序、top-k、检测数量上限和精确 NMS 保留。单视图 FP32 在固定最终阈值处有独立机制检查；这不保证 AMP 或融合整体零差异。

融合时低分成员仍能改变聚类、融合框和加权分数。原 FP32 完整 VAL 缓存的 `.35` 筛选诊断得到 P@R≥90＝94.2996%，低于原 94.4343%。那是旧缓存复算，不是 FP16 权重重推或速度测试。因此入口不会把 `.35` 作为默认值，也不把过滤称为无损。`.70`、`.75` 同样需要对应验证。

## 5. 用户或跟踪器给定的 512 局部窗口

中心使用**完整输入 RGB 的像素坐标**，由用户或跟踪器提供；没有 `--crop-center` 就使用全图，不会从 GT 或标注中寻找苹果中心。

```powershell
& $ApplePython -B .\scripts\predict_fast_image.py `
  --image 'F:\待识别图片\apple.jpg' `
  --output 'F:\苹果部署试验\local_001' `
  --model base --precision fp16 --pre-nms-threshold none `
  --crop-center 650 720 --crop-size 512 --short-side 512 --max-size 512
```

窗口靠近边缘时在图内平移，图像小于窗口时取实际可用范围，不填造图外像素。`metadata.json` 记录所给中心、实际独占右下边界的 `window_full_xyxy`、原图偏移和实际输入尺寸。框和掩膜窗口均映射回全图；NPZ 另保留 crop 内框。未输出的窗口外区域不能解释为没有苹果。

这属于局部跟踪/接近时的输入，不等于“把整幅果园图缩到 512”的实验，也没有已经通过局部目标漏检率或三维定位验收。

## 6. 加载、预热和计时

默认每个模型预热 1 次，可用 `--warmup-runs 0` 关闭。一次 CLI 进程内每模型只反序列化并恢复一次，预热和正式调用复用同一模型。重新启动另一条 CLI 命令仍需重新加载；这里没有宣称已实现常驻视频服务。

`metadata.json` 分别记录 SHA/加载/构建/恢复/GPU 传输、预热，以及一次 H2D＋前向＋CPU 校验耗时；导出 PNG/NPZ 不计入该前向记录。这些数值不能直接换算为稳定部署 FPS。需要比较速度时应使用固定设备、固定输入、充分预热及重复测量，并与精度验收结果一起报告。
